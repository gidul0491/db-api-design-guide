# 4장. 코드 구조와 규약

## 4-1 디렉터리 구성

1.  **디렉터리를 업무 단위로 먼저 나눌지 계층으로 먼저 나눌지 정하고, 전체에서 한 가지만 씁니다.**

    두 방식이 섞이면 같은 성격의 파일이 어디 있는지 매번 확인해야 합니다. 아래 두 항이 판단 근거입니다.
    ```
    업무 단위 우선                   계층 우선
    src/modules/                    src/
      employee/                       controllers/
        employee.router.js              employee.controller.js
        employee.controller.js          company.controller.js
        employee.service.js           services/
        employee.repository.js          employee.service.js
      company/                          company.service.js
      payroll/                        repositories/
    ```
2.  **업무 단위 우선은 하나의 업무를 고칠 때 열어야 할 파일이 한 폴더에 모입니다.**

    업무가 늘어도 폴더 안의 파일 수는 그대로입니다. 대신 업무 폴더끼리 서로를 부르기 시작하면 의존 관계가 눈에 보이지 않게 됩니다.

3.  **계층 우선은 같은 계층의 코드를 나란히 놓고 비교하기 쉽습니다.**

    계층별 규칙을 지키는지 한눈에 보이고, 업무가 서넛뿐인 작은 서비스에서는 폴더가 덜 깊습니다. 대신 업무가 늘면 한 업무의 코드가 폴더 서너 곳에 흩어집니다.

4.  **두 방식은 배타적이지 않습니다. 업무 단위로 먼저 나눈 뒤 모듈 안을 다시 계층으로 나눠도 됩니다.**

    큰 축에서 전체적인 순서가 같으면 1번 규칙을 지키는 것입니다. 하위 도메인은 계층 폴더 안에서 파일 이름으로 가릅니다. 다만 한 모듈의 하위 도메인이 열 개를 넘어가면 폴더를 한 겹 더 넣기 전에 모듈 경계가 맞는지부터 봅니다. 그쯤 되면 대개 그 모듈이 사실 여러 모듈입니다.
    ```
    업무 → 계층 → 하위 도메인

    src/modules/payroll-module/
      payroll.router.js
      dto/  constants/
      controller/    salary.controller.js · bonus.controller.js
      service/       salary.service.js · bonus.service.js
      repository/    salary.repository.js · bonus.repository.js
    ```
5.  **어느 쪽으로 정하든 여러 업무가 함께 쓰는 것은** `modules` **밖의** `shared` **폴더 한 곳에 둡니다.**

    미들웨어, 암복호화, 날짜 처리, 설정 읽기가 여기 해당합니다. 업무 폴더 안에 두면 다른 업무가 그 폴더 내부를 직접 부르게 되고, 그때부터 폴더 경계가 의미를 잃습니다.

    `shared` 안은 성격별로 나눕니다. `constants`에는 고정값을, `helpers`에는 암복호화·파일 처리처럼 외부와 통신하지 않는 순수 함수를, `infra`에는 DB·문자·메일·슬랙·SSH처럼 외부 통신에 기대는 기능을, `middlewares`에는 인증·로깅·오류 응답처럼 업무 로직 밖의 HTTP 처리를 둡니다. 외부와 통신하는지로 `helpers`와 `infra`를 가르면, 테스트에서 갈아 끼울 대상(7-4-4)이 `infra` 한 곳에 모입니다.

6.  **업무 폴더끼리는 서비스 계층을 통해서만 부릅니다.**

    다른 업무의 리포지토리를 직접 부르면 그 업무의 판단을 건너뛰게 됩니다. 어느 것을 고칠 때 무엇이 함께 깨지는지도 알 수 없게 됩니다.

## 4-2 파일과 심볼 이름

1.  **파일 이름에 계층을 붙입니다 —** `employee.service.js`**.**

    편집기에서 파일을 열 때 폴더 경로를 보지 않고도 무엇인지 압니다. `index.js`가 여러 개면 열린 탭만 보고는 구분되지 않습니다.

2.  **모듈 경로는 상대 경로 대신 별칭을 씁니다 —** `@shared/helpers/crypto`**.**

    `../../../shared/helpers/crypto`는 파일을 옮기는 순간 전부 깨지고, 몇 단계를 올라가는지 세면서 읽어야 합니다.

3.  **함수 이름은 무엇을 하는지로 짓고, 어떻게 하는지는 넣지 않습니다.**

    `findEmployeeByPhoneWithJoin`처럼 구현 방식이 이름에 들어가면 구현을 바꿀 때 이름이 거짓말을 하기 시작합니다.

4.  **조회 함수의 이름으로 결과의 개수를 구분합니다.**

    하나를 돌려주는 것과 목록을 돌려주는 것이 이름으로 갈리면, 부르는 쪽에서 결과를 잘못 다루는 일이 줄어듭니다. `findEmployee`와 `findEmployees`처럼 단수·복수로 가르거나 접두어를 정해 씁니다.

## 4-3 표기와 변환 지점

하나의 값은 DB·코드·URL을 지나는 동안 서로 다른 표기로 나타납니다. `company_id`가 코드에서는 `companyId`가 되고 경로에서는 또 달라집니다. 어느 자리에서 어떤 표기를 쓰는지, 그리고 표기가 바뀌는 지점이 어디인지 두 가지가 정해져 있어야 합니다.

1.  **한 값이 자리마다 어떤 표기로 나타나는지 표로 정해 둡니다.**

    정해 두지 않으면 같은 값이 자리마다 다른 표기로 나타나 검색이 되지 않습니다. `companyId`로 검색했을 때 응답 코드만 나오고 DB 접근 코드가 안 나오면, 그 값을 쓰는 자리를 전부 찾았는지 확신할 수 없습니다. 표기 자체는 무엇이든 됩니다. 정해 두는 것이 규칙입니다. 아래는 한 가지 예시일 뿐이라, 요청·응답 필드를 스네이크로 채워도 규칙은 지켜집니다.
    ```
    같은 값 하나가 자리마다 이렇게 나타난다

      DB 테이블·컬럼    company_employee · company_id   스네이크
      코드 변수·속성    companyId                       카멜
      함수·메서드       findCompanyEmployees            카멜
      클래스            CompanyEmployeeService          파스칼
      상수              MAX_PAGE_SIZE                   대문자 스네이크
      요청·응답 필드    companyId                       카멜
      쿼리스트링        ?companyId=12                   카멜
      URL 경로          /company-employees              케밥
      폴더명            company-employee-module         케밥
      파일명            company.service.js              점으로 계층 구분
    ```
2.  **표기가 바뀌는 지점을 정하고, 그 밖에서는 바꾸지 않습니다.**

    바뀔 수 있는 자리는 둘뿐입니다. **DB와 서버 코드 사이**(리포지토리 경계), 그리고 **서버 코드와 API 응답 사이**(직렬화)입니다. 여기서 서버 코드란 컨트롤러·서비스·리포지토리가 변수와 속성에 쓰는 표기를 말합니다. 서버 코드의 표기와 API 응답 필드의 표기를 같게 맞추면 직렬화 자리에서는 바꿀 것이 없습니다. 코드가 카멜인데 응답도 카멜이면 객체를 그대로 내보내면 되니까요. 응답만 스네이크로 정했다면 직렬화 자리에서 한 번 바꾸고, 그 밖에서는 바꾸지 않습니다. 리포지토리 경계 쪽은 대개 DB 라이브러리 설정으로 전역 적용하는 편이 안전합니다. 테이블마다 손으로 매핑하면 새 컬럼을 추가할 때 빠뜨립니다. 정한 지점 밖에서 변환하면 한 곳이 빠졌을 때 오류가 나지 않고 `undefined`가 되며, 그 값은 화면에서 그냥 빈칸으로 보입니다.
    ```
    repository   SELECT id, company_id, created_at FROM employee …
                 ↓  여기서 한 번 바꾼다
                 { id: 3, companyId: 12, createdAt: '2026-09-06 10:00:00' }
                 ↓
    service      companyId 만 본다
    controller   companyId 만 본다
    응답          { "companyId": 12 }
    ```
3.  **줄임말과 두문자어의 표기를 미리 정합니다.**

    `id`·`url`·`api`처럼 대문자로 쓰던 말이 카멜 케이스 안에 들어올 때 사람마다 다르게 씁니다. `companyId`와 `companyID`, `apiKey`와 `APIKey`가 함께 생기면 1번의 문제가 그대로 재현됩니다. 첫 글자만 대문자로 쓰는 쪽(`companyId`, `apiKey`, `pdfUrl`)을 기본으로 삼고, 예외를 두지 않습니다.

4.  **주석에는 왜 그렇게 했는지를 적습니다. 무엇을 하는지는 이름으로 말합니다.**

    코드를 읽으면 아는 것을 주석으로 되풀이하면, 코드가 바뀌었을 때 주석이 거짓말을 하기 시작합니다. 왜 그렇게 했는지는 코드에 남지 않아 주석으로만 전달됩니다.
