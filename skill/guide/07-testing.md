# 7장. 테스트

테스트하기 어려우면 대개 계층이 섞인 것입니다. 서비스가 HTTP를 모르면 요청 객체를 지어낼 필요가 없고, 리포지토리가 커넥션을 인자로 받으면 시험용 트랜잭션에 묶어 돌릴 수 있습니다. 5장을 지킨 대가가 여기서 돌아옵니다.

## 7-1 무엇을 테스트하는가

1.  **값을 만들어 내는 계산과 업무 판단에는 반드시 테스트를 붙입니다.**

    나이 계산, 급여 계산, 기간 판정, 유효 상태 판정 같은 것입니다. 여기가 틀리면 어디에서도 오류가 나지 않고 숫자만 조용히 틀립니다. 반대로 여기만 지켜지면 화면이 바뀌어도 값은 유지됩니다.

2.  **리포지토리는 실제 DB에 붙여 확인합니다. 질의를 흉내 낸 가짜로 대신하지 않습니다.**

    확인하려는 것이 질의가 맞는가인데, 가짜로 바꾸면 그 질의는 한 번도 실행되지 않습니다. 컬럼 이름 오타나 조인 조건 실수가 그대로 통과합니다.

3.  **컨트롤러는 따로 떼어 시험하지 않고, 요청부터 응답까지 한 줄로 훑습니다.**

    컨트롤러만 떼면 아래 계층을 전부 가짜로 채우게 되고, 남는 것은 가짜가 시킨 대로 동작하는지 확인하는 일뿐입니다. 경로 하나를 실제로 호출해 상태 코드와 응답 모양을 봅니다.

4.  **결함을 고칠 때는 그 결함을 재현하는 테스트를 먼저 만듭니다.**

    재현하지 못한 채 고치면 고쳐졌는지 확신할 수 없고, 같은 결함이 다시 들어오는 것도 막지 못합니다.

5.  **커버리지 숫자를 목표로 삼지 않습니다.**

    숫자를 맞추려 들면 값을 확인하지 않고 함수만 한 번씩 불러 보는 테스트가 생깁니다. 숫자 대신 1번에 적은 것들에 테스트가 있는지를 봅니다.

## 7-2 어디에 두는가

1.  **단위 테스트는 대상 파일 옆에 같은 이름으로 둡니다 —** `employee.service.test.js`**.**

    모듈을 옮길 때 테스트가 따라옵니다. 테스트가 없는 파일이 폴더에서 바로 눈에 띕니다.

2.  **여러 모듈에 걸치거나 서버를 띄워야 하는 테스트는 별도 폴더에 모읍니다.**

    어느 한 모듈의 것이 아니라 옆에 둘 자리가 없습니다. 실행 시간도 길어서 따로 돌릴 수 있어야 합니다.
    ```
    src/modules/employee/
      employee.service.js
      employee.service.test.js     단위
      employee.repository.js
      employee.repository.test.js  실제 DB 에 붙는다
    test/
      employee.api.test.js         서버를 띄워 HTTP 로 부른다
      helpers/
        db.js                      스키마 준비와 정리
        fixture.js                 시험 데이터 만들기
    ```
3.  **시험 데이터는 코드로 만듭니다. 덤프 파일에 기대지 않습니다.**

    덤프는 스키마가 바뀌면 조용히 낡습니다. 코드로 만들면 컬럼이 늘어난 순간 깨져서 알려 줍니다. 테스트마다 필요한 것만 만들고, 다른 테스트가 만들어 둔 것에 기대지 않습니다.

## 7-3 어떻게 쓰는가

1.  **테스트 이름에 조건과 기대 결과를 적습니다.**

    `근속 1년 미만 직원에게는 1개월 개근마다 연차 1일을 부여한다`처럼 씁니다. `테스트1`이나 `calculateAge 테스트`로는 실패 목록만 보고 무엇이 깨졌는지 알 수 없습니다.

2.  **테스트 하나는 한 가지만 확인합니다.**

    여러 개를 한 테스트에 담으면 첫 번째에서 실패했을 때 나머지가 맞는지 알 수 없습니다.

3.  **준비·실행·확인 세 토막으로 나눠 씁니다.**

    무엇을 준비했고 무엇을 불렀고 무엇을 기대하는지가 눈으로 갈리면, 실패한 테스트를 읽는 시간이 짧아집니다.

4.  **경계값을 넣습니다.**

    기간의 첫날과 마지막 날, 0과 음수, 빈 목록, 최대 길이입니다. 하루 차이로 갈리는 계산은 가운데 값으로는 드러나지 않습니다.

5.  **테스트끼리 서로의 결과에 기대지 않습니다.**

    순서에 기대면 하나가 실패할 때 뒤가 전부 실패해, 원인이 하나인지 여럿인지 알 수 없습니다. 아무거나 하나만 골라 돌려도 통과해야 합니다.

6.  **시각에 기대는 로직은 기준 시각을 인자로 받게 만듭니다.**

    함수 안에서 현재 시각을 직접 읽으면 자정 근처에 결과가 달라지고, 테스트가 어느 날에는 통과하고 어느 날에는 실패합니다. 원인을 찾는 데 가장 오래 걸리는 종류입니다.

## 7-4 DB와 외부 시스템

1.  **DB가 필요한 테스트는 시험 전용 스키마에 붙입니다.**

    개발 DB를 함께 쓰면 남이 넣어 둔 데이터 때문에 결과가 달라지고, 반대로 테스트가 남의 데이터를 지웁니다. 접속 정보는 설정에서 읽어 시험용만 바라보게 합니다.

2.  **커넥션을 인자로 넘겨 부르는 테스트는 하나를 트랜잭션으로 감싸고 끝나면 되돌립니다.**

    지우는 코드를 따로 쓰지 않아도 테스트 사이가 깨끗해집니다. 리포지토리가 커넥션을 인자로 받기 때문에(5-6-2) 시험 코드가 연 트랜잭션을 그대로 넘길 수 있습니다.

3.  **서버를 띄워 HTTP로 부르는 테스트에는 2번이 통하지 않습니다. 정리 방법을 따로 정합니다.**

    시험 코드가 연 트랜잭션과 서버가 요청을 처리하며 잡는 커넥션은 서로 다릅니다. 시험 코드에서 되돌려도 서버가 넣은 행은 그대로 남고, 반대로 아직 커밋되지 않은 시험 데이터는 서버 쪽에서 보이지 않아 없는 것으로 처리됩니다. 이쪽은 실행할 때마다 스키마를 새로 만들거나, 테스트가 끝날 때 자기가 만든 것을 지우거나, 실행 단위마다 스키마를 갈라 쓰는 방법 중 하나를 정합니다. 정하지 않으면 시험 데이터가 쌓여 어제는 통과하던 테스트가 오늘 실패합니다.

4.  **외부 시스템은 갈아 끼운 구현으로 부릅니다.**

    벤더를 바꿔 끼울 수 있게 나눠 둔 그 자리를 씁니다. 테스트를 돌렸는데 실제로 문자가 나가거나 결제가 일어나면 안 됩니다.

5.  **외부 호출의 실패도 시험합니다.**

    시간 초과, 거절 응답, 잘못된 형식입니다. 성공만 시험하면 재시도할 실패와 하지 말 실패를 가르는 판단이 한 번도 실행되지 않습니다.

## 7-5 실행

1.  `npm test` **하나로 전부 돌아가게 합니다.**

    새로 온 사람이 무엇을 어떤 순서로 돌려야 하는지 묻지 않아야 합니다. 준비가 필요하면 그 준비까지 그 명령 안에 넣습니다.

2.  **단위와 통합을 따로 돌릴 수 있게 나눕니다.**

    단위는 몇 초, 통합은 몇 분입니다. 고치는 중에는 짧은 쪽만 반복해 돌리고, 밀어 넣기 전에 전부 돌립니다.

3.  **테스트는 코드를 밀어 넣을 때 자동으로 돌게 겁니다.**

    사람이 기억해서 돌리는 테스트는 급할 때 건너뜁니다. 급할 때가 가장 위험한 때입니다.

4.  **실패한 테스트를 남겨 두지 않습니다.**

    깨진 채로 둔 테스트가 하나 생기면 그다음부터 실패 목록을 아무도 읽지 않습니다. 고치거나, 지금 맞지 않는 테스트라면 지웁니다.
