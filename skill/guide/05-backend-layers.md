# 5장. 백엔드 계층

한 파일에 모든 로직을 쓰면 처음에는 개발이 빠릅니다. 문제는 두 번째 화면부터입니다. 같은 조회가 필요한데 그 코드가 응답을 만드는 코드와 붙어 있어 같은 서비스 로직을 부를 수 없고, 결국 코드를 복사합니다. 복사한 뒤에는 하나가 바뀔 때 두 곳을 고쳐야 하고, 한 곳을 놓치면 화면마다 다른 값이 나옵니다.

계층은 이것을 막기 위해 코드를 자리별로 나눠 두는 것입니다. 나누는 기준은 "무엇을 하는가"가 아니라 **무엇을 모르는가**입니다. 각 계층이 모르는 것이 정해져 있으면, 그 계층은 자기가 모르는 것이 바뀌어도 고칠 필요가 없습니다.

- 라우터는 **업무를 모릅니다**. 그래서 업무 규칙이 바뀌어도 라우터는 그대로입니다.

- 컨트롤러는 **DB를 모릅니다**. 그래서 테이블 구조가 바뀌어도 컨트롤러는 그대로입니다.

- 서비스는 **HTTP를 모릅니다**. 그래서 화면이 아니라 배치에서 불러도 그대로 동작합니다.

- 리포지토리는 **왜 부르는지 모릅니다**. 그래서 어느 업무에서 불러도 같은 결과를 냅니다.

계층을 건너뛰거나 섞으면 이 성질이 무너집니다. 컨트롤러에 SQL이 한 줄 들어가는 순간 컨트롤러가 테이블을 알게 되고, 그때부터 테이블 이름을 바꾸려면 컨트롤러도 찾아 고쳐야 합니다.

## 5-1 계층별 입력과 출력

| 계층 | 입력 | 출력 | 모르는 것 |
|----|----|----|----|
| router | HTTP 요청 | 컨트롤러 호출 · 분기값 주입 | 업무 규칙, 테이블 |
| controller | req, res | HTTP 응답 (상태 + 본문) | SQL, 테이블 이름 |
| dto | 요청 값 / 서비스 결과 | 검증 통과값 / 내보낼 필드 | 업무 규칙 |
| service | 값(원시 타입·객체) + db | 업무 개념의 값 | req, res, HTTP 상태 |
| repository | db + 조건 값 | 테이블 행에 가까운 값 | 업무 규칙, 호출한 이유 |

한 요청이 계층을 지나며 값이 어떻게 바뀌는지가 아래입니다. 어느 계층에 무엇을 둘지 헷갈리면 이 흐름의 어느 칸에 해당하는지를 봅니다.
```
GET /api/company-employees?companyId=12&page=1

router        경로를 확인하고 인증 미들웨어를 태운다
              경로가 정하는 분기값(대상 DB 등)을 넘길 준비를 한다
    │  req, res
    ▼
controller    요청 dto 로 쿼리스트링을 검증한다
              → { companyId: 12, page: 1, size: 20 }
    │  ({ companyId: 12, page: 1, size: 20 }, db, user)
    ▼
service       업무 판단 — 이 사용자가 이 회사를 볼 수 있는가
              page 를 offset 으로 바꾼다
    │  (db, { companyId: 12, offset: 0, limit: 20 })
    ▼
repository    SELECT id, name, phone_encrypted … WHERE company_id = ?
    │  [ { id: 3, name: '홍길동', phoneEncrypted: 'aes256.gcm.…' }, … ]
    ▲
service       전화번호를 복호화해 가린 값으로 바꾼다
    │  [ { id: 3, name: '홍길동', phone: '010-****-5678' }, … ]
    ▲
controller    응답 dto 로 내보낼 필드를 고르고 상태 코드를 정한다
    │  200 { data: [ … ], pagination: { page: 1, size: 20, total: 137 } }
    ▲
```
## 5-2 router

1.  **라우터에는 경로 정의와 미들웨어 배치만 둡니다.**

    라우터에 조건문이 생겼다면 그것은 컨트롤러의 일입니다. 라우터가 얇으면 그 파일 하나가 모듈의 목차 역할을 해서, 이 모듈이 무슨 경로를 갖고 있고 어디에 인증이 걸려 있는지 한눈에 보입니다.

2.  **요청마다 달라지는 분기값은 라우터에서 정해 아래로 넘깁니다 — 대상 DB, 대상 환경 같은 것.**

    경로 파라미터가 그 값을 갖고 있으니 판단도 라우터에 둡니다. 아래 계층이 스스로 고르면 같은 함수를 다른 대상에 쓸 수 없고, 대상이 하나 늘 때마다 그 함수들을 전부 찾아 고쳐야 합니다. 다만 DB가 하나뿐인 시스템은 여기 해당하지 않습니다. 커넥션은 시작할 때 한 번 잡아 두고 리포지토리가 그대로 쓰면 됩니다. 그리고 배치와 스케줄러에는 요청이 없으므로, 그쪽이 같은 값을 어디서 얻을지도 함께 정해 둡니다.

3.  **인증 미들웨어는 라우터에서 걸고, 새 경로는 기본적으로 인증 대상에 넣습니다. 인증이 필요 없는 경로만 따로 모아 인증 미들웨어보다 앞에 등록합니다.**

    미들웨어는 등록 순서대로 걸리므로, 순서를 잘못 두면 인증을 걸려던 경로가 공개됩니다. 기본을 인증 대상으로 두면 실수했을 때 공개되는 대신 인증이 걸립니다. 막혀서 못 쓰는 것은 바로 알려지지만, 열려 있는 것은 아무도 알려주지 않습니다.

## 5-3 controller

1.  **컨트롤러는 두 가지만 합니다 — "제대로 들어왔나"와 "어떻게 돌려줄까".**

    앞은 요청 DTO 검증이고 뒤는 응답 규격과 상태 코드입니다. 이 둘 밖의 일이 컨트롤러에 있으면 그것은 다른 계층의 일입니다.

2.  **컨트롤러는 테이블 이름과 SQL을 모릅니다.**

    컨트롤러가 테이블을 알게 되면 스키마를 고칠 때 고쳐야 할 파일이 리포지토리 밖으로 번집니다.

3.  **서비스에서 받은 결과를 응답 규격으로 옮기기만 하고, 값을 더하거나 조건을 붙이지 않습니다.**

    여기서 값을 만들기 시작하면 같은 업무를 다른 경로나 배치에서 부를 때 그 처리가 빠집니다. 화면에 필요한 값이 모자라면 컨트롤러에서 채우지 말고 서비스가 내주게 합니다.

4.  **표시 가공은 컨트롤러가 하고, 노출 범위를 줄이는 것은 서비스가 합니다.**

    날짜 포맷을 바꾸거나 하이픈을 넣는 것은 컨트롤러입니다. 민감정보를 가리는 것은 서비스입니다. 둘 다 보여주는 모양처럼 보이지만 뒤쪽은 보안 경계를 넘습니다. 컨트롤러가 가리려면 평문을 받아야 하는데, 평문이 서비스 밖으로 나오는 순간 행을 통째로 내보내는 코드 한 줄이면 유출입니다. 서비스가 가려서 주면 컨트롤러는 평문을 쥔 적이 없어 실수로도 흘릴 수 없습니다. 평문을 정말 내보내야 하는 응답이라면 서비스가 평문을 주고 응답 DTO에 그 필드를 선언합니다. 그 선언 자체가 이 응답은 평문을 내보낸다는 기록이 됩니다.

5.  **오류는 직접 응답으로 만들지 않고 다음으로 넘깁니다.**

    컨트롤러마다 오류를 붙잡아 응답을 만들면, 그 컨트롤러를 쓰지 않는 경로에서 같은 오류가 다르게 나갑니다. 넘기기만 하면 처리 방식은 6-4가 한 곳에서 정합니다.

6.  **인증된 사용자 정보와 라우터가 정한 분기값을 서비스에 인자로 넘깁니다.**

    서비스가 요청 객체에서 직접 꺼내면 서비스가 HTTP를 알게 됩니다. 필요한 값만 뽑아 넘기면 배치에서 같은 서비스를 그대로 부를 수 있습니다.

## 5-4 dto

1.  **DTO는 통신 규격입니다. 요청 DTO는 들어오는 것을 막는 관문이고, 응답 DTO는 나가는 것을 고르는 관문입니다.**

    두 방향 모두 "선언되지 않은 것은 통과하지 않는다"가 핵심입니다. 이 관문이 없으면 요청 본문이 그대로 저장에 흘러가고, 조회한 행이 그대로 응답에 실립니다.

2.  **DTO는 형식만 봅니다. 업무 규칙은 보지 않습니다.**

    이 구분이 가장 헷갈리는 자리입니다. "값이 숫자인가", "필수인가", "날짜 형식이 맞는가"는 DTO입니다. "이 회사가 이 복리후생 플랜을 쓸 수 있는가", "이미 신청한 건인가"는 서비스입니다. 판단 기준은 **DB를 봐야 아는가**입니다. 봐야 알면 DTO가 아닙니다.

3.  **요청 DTO에 선언되지 않은 필드는 버립니다.**

    화면이 보내지 않기로 한 필드를 직접 넣어 보내는 것만으로 값이 바뀌는 것을 막습니다.

4.  **URL 파라미터와 쿼리스트링도 DTO로 검증합니다.**

    본문만 검증하고 넘어가는 경우가 많습니다. 경로의 `:id`에 숫자가 아닌 값이 들어오면 그대로 질의문까지 내려갑니다.

5.  **응답 DTO에 선언되지 않은 값은 내보내지 않습니다.**

    비밀번호 해시와 암호문 컬럼이 여기서 걸러집니다. 조회한 행을 통째로 돌려주는 코드가 한 곳만 있어도 그 값들이 밖으로 나갑니다. 다만 화면에 필요한 값이 선언에서 빠지면 조용히 사라지므로, 필드를 추가할 때 함께 확인합니다.

6.  **응답 DTO는 모듈 안에서 재사용하고, 화면마다 새로 만들지 않습니다.**

    같은 자원을 두 화면이 다른 DTO로 내보내면 필드 이름과 형식이 조금씩 갈립니다. 화면마다 필요한 필드가 다르면 DTO를 나누는 대신 내보낼 필드 목록을 인자로 받습니다.

## 5-5 service

1.  **서비스는 HTTP를 모릅니다.** `req`**·**`res`**를 넘기지 않습니다.**

    서비스가 HTTP를 알면 배치나 스케줄러에서 같은 업무를 부를 수 없습니다. 문자 발송 배치가 화면과 같은 판단을 해야 하는 경우가 반드시 생깁니다.

2.  **업무 판단은 전부 서비스에 있습니다.**

    "무엇이 유효한 상태인가", "이 값을 어떻게 계산하는가", "이 사람이 이 건을 볼 수 있는가"가 여기 해당합니다. 같은 판단이 두 곳에 있으면 한쪽만 고치는 일이 생기고, 같은 데이터인데 화면마다 다른 값이 나옵니다.

3.  **서비스는 SQL을 조립하지 않습니다.**

    조건이 하나 더 필요하면 리포지토리에 함수를 추가합니다. 서비스에 질의가 들어오기 시작하면 리포지토리는 껍데기만 남고, 어떤 질의가 나가는지 세는 것부터 되지 않습니다.

4.  **서비스가 다른 서비스를 부르는 것은 됩니다. 다만 트랜잭션을 넘기는 방법을 정해 둡니다.**

    같은 트랜잭션 안에서 다른 업무를 불러야 할 때, 트랜잭션 객체를 인자로 받을지 아니면 부르는 쪽이 전부 묶을지 한 가지로 정합니다. 정하지 않으면 안쪽 서비스가 별도 트랜잭션을 열어 바깥이 실패해도 되돌아가지 않습니다.

5.  **값을 만들어 내는 계산은 함수 하나로 만들어 한 번만 둡니다.**

    나이 계산, 급여 계산, 기간 판정처럼 결과가 화면에 그대로 보이는 것들입니다. 여러 서비스가 함께 쓰면 공용 모듈로 올립니다.

6.  **계산해서 만든 값도 테이블에서 읽어 온 행과 같은 형태로 돌려줍니다.**

    나중에 저장을 계산으로 바꾸거나 그 반대로 바꿔도, 불러 쓰는 코드를 고치지 않아도 됩니다. 1-1-3에서 "판단이 서지 않으면 저장하지 않는 쪽"을 고를 수 있는 것도 이 규칙이 받쳐 주기 때문입니다.

## 5-6 repository

1.  **질의 하나에 함수 하나입니다.**

    함수 하나가 조건에 따라 다른 질의를 만들기 시작하면, 그 안에 업무 판단이 들어온 것입니다. 실행 계획을 확인할 때도 어떤 질의가 나가는지 알 수 없습니다.

2.  **모든 함수는 첫 인자로** `db`**를 받고, 스스로 커넥션을 고르지 않습니다.**

    커넥션을 안에서 고르면 트랜잭션 안에서 부를 수 없습니다. 트랜잭션은 커넥션을 잡고 있는 객체이고, 그것을 받아 써야 같은 트랜잭션에 들어갑니다.

3.  **리포지토리는 왜 부르는지 모릅니다. 업무 판단을 하지 않습니다.**

    "유효한 것만 조회"처럼 들리는 조건도 대부분 업무 판단입니다. 무엇이 유효한지가 업무 규칙이기 때문입니다. 조건 값을 인자로 받아 그대로 거는 것이 리포지토리의 일입니다.

4.  **테이블 행에 가까운 값을 돌려주고, 화면에 맞춘 가공은 하지 않습니다.**

    화면에 맞춰 가공한 결과를 돌려주면 화면이 하나 늘 때마다 리포지토리 함수가 하나 늘고, 같은 조회가 여러 벌 생깁니다.

5.  `SELECT *`**를 쓰지 않고 필요한 컬럼만 적습니다.**

    컬럼이 추가되면 그 값이 응답까지 그대로 흘러갈 수 있고, 암호문 컬럼이 여기 섞여 나갑니다. 어떤 컬럼을 쓰는지가 코드에 적혀 있어야 스키마를 고칠 때 영향 범위를 셀 수 있습니다.

6.  **목록을 가져온 뒤 행마다 다시 조회하지 않습니다.**

    20건을 조회하고 각 건의 소속을 하나씩 조회하면 질의가 21번 나갑니다. 조인하거나 식별자를 모아 한 번에 조회합니다.

## 5-7 계층 경계

1.  **업무를 처리하는 경로는 계층을 모두 채웁니다. 간단하다는 이유로 계층을 건너뛰지 않습니다.**

    건너뛰면 업무 판단이 컨트롤러나 질의문에 섞여 들어가고, 다음에 같은 판단이 필요한 사람은 그것을 찾지 못해 다시 씁니다. 다만 헬스 체크처럼 업무 판단도 DB 접근도 없는 경로는 라우터에서 바로 응답해도 됩니다.

2.  **한 계층은 바로 아래 계층만 부릅니다. 컨트롤러가 리포지토리를 직접 부르지 않습니다.**

    건너뛴 호출이 하나 생기면 그 뒤로 계속 늘어납니다. 조회만 하니까 괜찮다고 생각한 자리에 나중에 업무 판단이 붙습니다.

3.  **아래 계층이 위 계층을 부르지 않습니다.**

    리포지토리가 서비스를 부르기 시작하면 호출이 순환하고, 어느 쪽부터 읽어야 하는지 정해지지 않습니다.

4.  **파일이 하나뿐이어도 계층 폴더를 유지합니다.**

    지금 짧다고 폴더를 합치면, 커졌을 때 쪼개는 일이 파일을 옮기고 참조를 전부 고치는 일이 됩니다. 처음부터 자리가 나뉘어 있으면 파일만 늘리면 됩니다.

5.  **기능이 늘면 계층 폴더 안에서 관심사별로 파일을 쪼갭니다.**

    `controller/salary.controller.js`, `controller/bonus.controller.js`처럼 나눕니다. 한 파일이 커지는 것을 계층을 늘려 해결하지 않습니다.

6.  **새 모듈은 아래에서 위로 만듭니다 — 리포지토리 → 서비스 → DTO → 컨트롤러 → 라우터.**

    위에서 시작하면 아래 계층이 무엇을 돌려줄지 정해지지 않은 채로 응답 모양을 먼저 정하게 되고, 결국 컨트롤러에서 값을 맞추게 됩니다.

## 5-8 트랜잭션

1.  **트랜잭션은 서비스 계층에서만 시작하고 끝냅니다.**

    리포지토리가 각자 트랜잭션을 열면, 여러 테이블을 함께 바꾸는 작업이 중간까지만 저장된 채로 끝날 수 있습니다.

2.  **트랜잭션 안에서 외부 시스템을 부르지 않습니다.**

    외부 호출은 느리고 언제 끝날지 모릅니다. 그동안 잠금이 유지되어 다른 요청이 밀립니다. 외부 호출이 실패해도 트랜잭션은 되돌릴 수 있지만, 성공한 외부 호출은 되돌릴 수 없다는 점도 함께 고려해야 합니다.

3.  **트랜잭션은 필요한 만큼만 감싸고 조회만 하는 코드는 넣지 않습니다.**

    범위가 넓을수록 잠금이 오래 유지되고 교착이 생길 확률이 올라갑니다.

4.  **여러 요청이 같은 행을 동시에 바꿀 수 있는 업무는 그 사실을 먼저 인정하고 막을 방법을 정합니다.**

    재고 차감, 순번 발급, 잔액 갱신, 중복 신청이 여기 해당합니다. 조회한 값을 그대로 계산해 저장하는 코드는 두 요청이 겹치면 한쪽 결과가 사라집니다. 화면에서 두 번 눌리는 것만으로도 재현됩니다.

5.  **같은 요청이 두 번 들어와도 결과가 한 번과 같아야 하는 API는 그렇게 만듭니다.**

    응답이 늦으면 사용자는 다시 누르고, 네트워크는 같은 요청을 두 번 보냅니다. 요청마다 식별자를 받아 이미 처리한 것인지 확인하거나, 유니크 제약으로 두 번째를 막습니다.

## 5-9 외부 시스템 호출

1.  **외부 시스템을 부르는 코드는 별도 모듈로 감싸고, 서비스는 그 모듈만 부릅니다.**

    외부 API의 응답 형태가 서비스 코드 안까지 들어오면, 상대가 규격을 바꿀 때 고칠 자리가 여러 곳이 됩니다.

2.  **벤더가 바뀔 수 있는 것은 구현을 갈아 끼울 수 있게 나눕니다 — 문자, 메일, 파일 저장소.**

    부르는 쪽은 `send(번호, 내용)`만 알고, 어느 벤더로 나가는지는 설정이 정합니다. 벤더를 바꿀 때 부르는 코드를 고치지 않아도 되고, 로컬에서는 실제로 나가지 않는 구현으로 바꿔 끼울 수 있습니다.

3.  **모든 외부 호출에 시간 제한을 겁니다.**

    제한이 없으면 상대가 응답하지 않을 때 우리 쪽 요청도 함께 멈춰 있습니다. 그런 요청이 쌓이면 커넥션이 동나고 서비스 전체가 멈춥니다.

4.  **재시도할 실패와 하지 말 실패를 구분합니다.**

    연결이 끊긴 것은 다시 걸면 되지만, 상대가 "잘못된 요청"이라고 답한 것은 몇 번을 걸어도 같습니다. 구분하지 않고 재시도하면 상대 시스템에 같은 잘못된 요청을 계속 보냅니다.

5.  **응답을 기다릴 필요가 없는 일은 요청 처리에서 떼어 냅니다 — 문자·메일 발송, 파일 생성, 외부 전송.**

    요청 처리 안에서 하면 사용자가 그 시간만큼 기다리고, 발송이 실패하면 저장까지 함께 실패합니다.

6.  **떼어 낸 일은 큐나 작업 테이블에 넣고, 상태와 시도 횟수와 마지막 실패 이유를 남깁니다.**

    같은 프로세스에서 나중에 처리하는 방식은 그 프로세스가 재시작되면 남은 일이 사라집니다. 실패한 작업이 몇 건이고 왜 실패했는지 물어볼 곳도 필요합니다.

## 5-10 스케줄러

1.  **스케줄러는 자기 안에 업무 로직을 두지 않고 서비스를 부릅니다.**

    화면에서 하는 일과 배치가 하는 일이 같은 판단을 써야 합니다. 스케줄러가 따로 계산하면 화면과 배치가 다른 값을 내놓습니다.

2.  **주기 실행 작업은 겹쳐 도는 것을 막습니다.**

    앞선 실행이 아직 끝나지 않았는데 다음 실행이 시작되면 같은 대상을 두 번 처리합니다. 실행 중임을 표시하고 시작 전에 확인하거나, 처리 대상을 집을 때 잠금을 겁니다.

3.  **스케줄러를 켤지 말지를 설정으로 가릅니다.**

    설정 없이 앱과 함께 무조건 뜨면, 로컬에서 서버만 띄워도 운영 데이터를 폴링하고 문자나 메일이 실제로 나갑니다. 개발자가 코드를 주석 처리해 가며 막게 되고, 그 주석이 그대로 커밋됩니다.

4.  **실행 주기는 코드에 박지 않고 설정에서 읽습니다.**

    운영 중에 주기를 바꿔야 하는 일이 생깁니다. 코드에 박혀 있으면 배포해야 바뀝니다.
