# 6장. API 규약

## 6-1 경로와 메서드

1.  **경로는 자원 이름으로 만들고, 조회·등록·수정·삭제는 HTTP 메서드로 가릅니다.**

    화면마다 전용 경로를 만들면 같은 자원을 조회하는 경로가 여럿 생깁니다. 그 자원의 조회 조건이나 반환 항목을 하나 고칠 때마다 경로 수만큼 같은 수정을 반복하게 됩니다.

2.  **자원을 만들고 지우는 것으로 표현되지 않는 업무 행위는, 그 행위 이름을 그대로 쓴 경로로 둡니다 —** `POST /orders/{id}/cancel`**.**

    승인·취소·확정·반려가 여기 해당합니다. 억지로 수정으로 표현하면 무엇이 바뀌는 수정인지 본문을 열어 봐야 알 수 있고, 권한도 따로 걸 수 없습니다.

3.  **경로에 동사나 화면 이름을 넣지 않습니다 —** `/getEmployeeList`**,** `/employeePage`**.**

    화면이 바뀌면 경로가 남습니다. 화면 이름으로 만든 경로는 화면을 없앤 뒤에도 지워도 되는지 아무도 모릅니다.

4.  **경로를 합칠지는 세 가지로 판단합니다 — 반환하는 행의 단위가 같은가, 인증 주체가 같은가, 차이가 파라미터로 표현되는가.**

    셋 중 하나라도 아니면 사실 다른 자원이고, 억지로 합치면 조건 분기가 경로 안에 쌓입니다. 특히 인증 주체가 다르면 같은 자원이라도 열어 줄 필드 범위가 달라, 합쳤다가 조건 하나가 빠지면 그대로 노출됩니다.

5.  **목록 조회의 페이지 나눔·정렬·검색 조건 파라미터 이름을 프로젝트 전체에서 하나로 고정합니다.**

    경로마다 다르면 화면 코드가 경로마다 다른 형태를 만들어야 하고, 공통 목록 컴포넌트를 쓸 수 없습니다.

## 6-2 요청 검증

1.  **날짜·시각·금액처럼 형식이 갈리는 값은 주고받는 형식을 정해 둡니다.**

    같은 날짜를 어떤 화면은 `2026-09-06`으로, 어떤 화면은 `20260906`으로 보내기 시작하면 서버가 양쪽을 다 받아 주게 되고, 그때부터 어느 쪽이 규격인지 사라집니다.

2.  **시각에는 시간대를 붙여 주고받습니다. 붙이지 않기로 했다면 어느 시간대의 값인지를 명세에 못 박습니다.**

    `2026-09-06 14:22:10`만 받은 쪽은 이것이 어느 시간대의 14시인지 알 방법이 없습니다. 양쪽이 같은 나라에 있는 동안은 드러나지 않다가, 상대 서버가 UTC로 도는 환경으로 옮겨 간 날부터 아홉 시간씩 어긋난 값이 들어옵니다. `2026-09-06T14:22:10+09:00`처럼 오프셋을 붙이면 값이 스스로 답을 갖고 있어 그럴 일이 없고, 상대가 어느 언어를 쓰든 표준 함수로 그대로 읽습니다. 국내 전용 연동이라 오프셋 없이 가기로 했다면 명세 앞쪽에 시간대를 적고 모든 예시를 그 형식으로 통일합니다. 2-4-7이 DB와 서버 안쪽의 시간대를 맞추는 규칙이라면, 이것은 그 값이 밖으로 나갈 때의 규칙입니다.

3.  **목록 조회에 개수 상한을 둡니다.**

    상한이 없으면 전체를 요청하는 호출 하나가 서버와 DB를 함께 세웁니다. 화면이 요청한 개수를 그대로 믿지 않고 상한으로 자릅니다.

4.  **질의문은 파라미터 바인딩으로만 만듭니다. 값을 문자열로 이어 붙이지 않습니다.**

    이어 붙이는 방식은 값 안에 질의문을 넣어 보내는 것을 막지 못합니다. 한 곳만 있어도 DB 전체가 열립니다.

## 6-3 응답

1.  **성공과 실패 응답의 형태를 프로젝트 전체에서 하나로 고정합니다.**

    예외가 하나 생기면 그 예외를 아는 사람만 그 경로를 쓸 수 있게 됩니다.

2.  **성공했는지를 본문에 다시 담지 않습니다. 그 답의 정본은 HTTP 상태 코드입니다.**

    `success` 같은 결과 표시 필드를 두면 같은 사실이 두 곳에 저장된 것이 되고, 1장이 말하는 대로 언젠가 갈립니다. 갈리는 방향도 정해져 있습니다. `200`에 `success: false`를 담는 경로가 생기고, 그때부터 게이트웨이·캐시·모니터링·오류 추적 도구가 그 요청을 전부 성공으로 셉니다. 장애가 나도 실패율 그래프가 움직이지 않아 아무도 모릅니다. 성공 응답에는 요청한 자원만 담습니다.

3.  **실패 응답의 형태는 RFC 9457을 따르고,** `Content-Type`**은** `application/problem+json`**으로 내보냅니다.**

    오류 본문 규격을 새로 만들 이유가 없습니다. 표준 형식이면 상대가 설명을 읽지 않아도 어느 필드가 무엇인지 알고, 만들어져 있는 클라이언트 라이브러리가 그대로 해석합니다. 필드는 `type`(오류 종류를 가리키는 URI, 없으면 `about:blank`), `title`(사람이 읽는 짧은 이름), `status`(HTTP 상태와 같은 값), `detail`(이번 경우에 대한 설명), `instance`(문제가 난 자원의 경로)입니다. 필요한 필드를 더 붙일 수 있게 되어 있으므로 업무 오류 코드는 `code`로 더하고, 필드별 검증 실패처럼 여러 건을 알려야 하면 `errors` 배열을 더합니다. 화면은 `code`로 분기합니다. 메시지 문자열을 비교해 분기하면 문구를 다듬는 순간 분기가 깨집니다.
    ```
    409 Conflict
    Content-Type: application/problem+json

    {
      "type": "https://api.example.com/problems/duplicated-employee",
      "title": "이미 등록된 직원",
      "status": 409,
      "detail": "같은 회사에 같은 주민등록번호가 이미 등록되어 있습니다",
      "instance": "/api/external/employees",
      "code": "DUPLICATED_EMPLOYEE"
    }
    ```
4.  **목록 응답에는 전체 건수와 현재 위치를 함께 담습니다.**

    화면이 페이지 번호를 그리려면 전체 건수가 필요합니다. 따로 부르게 하면 두 번의 호출 사이에 데이터가 바뀌어 개수와 목록이 어긋납니다. 배열만 내보내면 이 값들을 담을 자리가 없으므로 목록은 객체로 감쌉니다. 이때 감싸는 필드는 결과를 담는 자리이지 성공을 알리는 표시가 아닙니다.

5.  **이미 쓰이고 있는 응답 필드는 이름을 바꾸거나 없애지 않습니다.**

    화면과 서버는 동시에 배포되지 않습니다. 필요하면 새 필드를 추가해 함께 내려보내다가 옛 필드를 뗍니다.

6.  **API 명세는 코드에서 만들어 냅니다.**

    손으로 쓴 문서는 나중에 실제와 갈립니다. 코드와 DTO가 곧 문서입니다.

## 6-4 오류 처리

1.  **예상한 실패와 예상하지 못한 실패를 다른 방식으로 다룹니다.**

    "이미 신청한 건입니다"는 업무 규칙이고 사용자에게 그대로 보여줘야 합니다. 데이터베이스 연결이 끊어진 것은 사용자가 할 수 있는 일이 없고, 내부 내용을 보여줘도 안 됩니다. 둘을 같은 방식으로 다루면 내부 오류 메시지가 화면에 나가거나, 업무 안내가 "오류가 발생했습니다"로 뭉개집니다.

2.  **업무 규칙 위반은 전용 오류 형태로 만들어 던지고, 컨트롤러가 아니라 공통 처리기에서 응답으로 바꿉니다.**

    경로마다 오류를 응답으로 바꾸면 형태가 조금씩 달라집니다. 한 곳에서 바꾸면 응답 규격이 저절로 지켜집니다.

3.  **예상하지 못한 실패는 전체를 잡아내는 처리기를 마지막에 두고, 여기서 로그를 남기고 일반적인 응답을 내려줍니다.**

    처리기가 없으면 스택 트레이스가 그대로 응답에 실려 나가고, 그 안에 파일 경로와 쿼리가 들어 있습니다.

4.  **오류를 삼키지 않습니다. 붙잡았으면 다루거나 다시 던집니다.**

    붙잡아 놓고 아무것도 하지 않은 자리는 나중에 문제가 생겼을 때 아무 흔적도 남기지 않습니다. 원인을 찾는 데 가장 오래 걸리는 종류의 결함이 여기서 나옵니다.

5.  **오류 로그에는 무엇이 잘못됐는지에 더해 그때 어떤 값이었는지를 남깁니다.**

    오류 메시지만 있으면 재현을 못 합니다. 요청 식별자를 남겨 그 요청의 다른 줄과 이어 붙이고(6-6-1), 판단에 쓰인 값을 함께 적습니다. 요청 본문은 6-6-3에 따라 가려서 남깁니다.

## 6-5 인증과 인가

1.  **인증 주체가 다르면 다른 미들웨어를 타게 합니다.**

    내부 사용자, 고객사 사용자, 링크만 들고 오는 외부 사용자는 확인해야 할 것과 열어 줄 범위가 모두 다릅니다.

2.  **인증과 인가를 나눠서 겁니다. 인증은 미들웨어에서, "이 사람이 이 건을 볼 수 있는가"는 서비스 계층에서 확인합니다.**

    로그인했다는 사실만으로는 남의 건을 열어도 되는지 알 수 없습니다. 경로에 붙은 식별자가 그 사람의 것인지는 데이터를 읽어 봐야 알 수 있고, 그것은 업무 판단이라 서비스 계층의 일입니다. 미들웨어에서만 막으면 `/orders/1234`의 숫자를 바꿔 남의 주문을 여는 문제가 그대로 남습니다.

3.  **조회 조건에 소속을 항상 함께 넣습니다.**

    식별자로만 조회하면 그 행이 다른 소속의 것이어도 결과가 나옵니다. 조회 단계에서 소속을 함께 걸면 인가 확인을 빠뜨려도 애초에 행이 나오지 않습니다.

4.  **처리자 값은 인증된 세션에서 가져옵니다. 화면에서 넘어온 값을 쓰지 않습니다.**

    화면에서 넘어온 값을 그대로 저장하면 기록을 조작할 수 있습니다.

5.  **관리자 기능은 경로를 숨기는 것이 아니라 권한으로 막습니다.**

    경로를 모를 것이라는 가정은 화면 코드가 브라우저에 내려가는 순간 깨집니다.

## 6-6 로그

1.  **요청마다 식별자를 하나 붙이고, 그 요청이 남기는 모든 줄에 함께 적습니다.**

    식별자가 없으면 여러 요청이 동시에 남긴 줄이 섞여, 하나의 요청이 무엇을 했는지 이어서 읽을 수 없습니다. 앞단에서 이미 붙여 보낸 식별자가 있으면 그것을 그대로 이어받고, 외부 시스템을 부를 때도 함께 넘깁니다. 장애가 났을 때 상대 쪽 로그와 맞춰 볼 수 있는 유일한 열쇠입니다.

2.  **요청과 응답을 남깁니다 — 시각, 요청 식별자, 메서드, 경로, 상태 코드, 처리 시간, 요청 헤더와 본문, 응답 헤더와 본문.**

    이것을 남기지 않으면 "우리는 분명히 보냈다"와 "우리는 받은 적 없다"가 맞설 때 답할 방법이 없습니다. 외부 연동에서는 이 기록이 있느냐 없느냐가 책임 소재를 가릅니다. 화면에서 무엇을 눌렀길래 그 값이 저장됐는지도 요청 본문이 있어야 답합니다. 처리 시간을 함께 남기면 느려진 경로를 따로 재는 장치 없이도 찾아냅니다.

3.  **남기기 전에 민감정보를 가립니다. 가릴 필드 목록은 코드 한 곳에 두고 거기서만 고칩니다.**

    비밀번호, 주민등록번호, 전화번호, 카드번호, 그리고 `authorization`·`cookie`·`x-api-key` 같은 인증 헤더입니다. 목록이 여러 곳에 흩어지면 새 필드가 한쪽에만 추가되고, 빠진 쪽으로 평문이 그대로 남습니다. 로그는 3장이 막아 둔 것을 가장 쉽게 우회하는 경로입니다. 암호화해 저장한 값이 로그에는 평문으로 남아 있는 일이 실제로 자주 일어납니다.

4.  **본문이 크면 잘라서 남기고, 파일 본문은 남기지 않습니다.**

    길이 상한을 정해 두고 넘으면 잘린 것을 표시합니다. 업로드 본문을 그대로 남기면 로그가 며칠 만에 디스크를 채우고, 그때는 로그를 지우는 것 말고 할 수 있는 일이 없습니다.

5.  **한 줄에 하나의 사건을, 기계가 읽을 수 있는 형태로 남깁니다.**

    문장으로 이어 붙인 로그는 사람이 눈으로 읽을 때만 쓸모가 있습니다. 필드로 나눠 두면 요청 식별자나 상태 코드로 걸러 볼 수 있고, 여러 줄에 걸친 오류 기록도 하나로 묶입니다. 여러 대로 나눠 도는 서버에서는 이것이 없으면 로그를 모아 놓아도 볼 수가 없습니다.

6.  **로그의 보관 기간을 정합니다. 열람 이력과 같은 자리에 두지 않습니다.**

    로그는 기간이 지나면 지워지는 것이 정상입니다. 나중에 조회해서 답해야 하는 자료는 3-4-2에 따라 테이블에 남깁니다. 둘을 섞으면 지워도 되는 것을 못 지우거나, 남겨야 할 것이 함께 사라집니다.
